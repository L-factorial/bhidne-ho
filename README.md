# Bhidne Ho — Multiplayer foundation and standalone Call Break

A Python/FastAPI multiplayer foundation plus an independent Call Break engine.
The platform provides authentication, rooms, presence, WebSockets and serialized
command handling. The standalone engine implements four- and five-player games,
five deals, bidding, tricks, scoring, configurable redeals, public queries and replay.
The browser console includes a separate Call Break test host with four/five-player
lobbies and three-second automatic actions. Chat and PING still use EchoGameEngine;
the shared adapter handles full gameplay; production runtime integration remains separate work.

## Run locally

Python 3.11 or newer:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
uvicorn app.main:app --reload --workers 1
```

Health: `GET http://127.0.0.1:8000/health`. HTTP API docs: `/docs`.
Use **one worker**: credentials, rooms, and sockets are process-local. Restarting
(including reload) discards credentials and presence. Ad hoc rooms are created on first
connection and removed when empty; explicitly created rooms remain in the directory
until restart. Rooms are open to any authenticated guest.

## Connect multiple clients

In two or more terminals, from this directory:

```sh
source .venv/bin/activate
python scripts/client.py demo
```

Each client obtains its own identity. Wait for `CONNECTED` in each terminal, then
type `hello` in one. Every other identity in `demo` receives the message. The sender
does not receive an echo. Run a third client with `python scripts/client.py other`
to check room isolation. Type `/quit` or close a client to leave.

For browser tabs, open `/docs` and run this in each tab's developer console:

```js
const guest = await fetch('/auth/guest', {method: 'POST'}).then(r => r.json());
const scheme = location.protocol === 'https:' ? 'wss:' : 'ws:';
const socket = new WebSocket(`${scheme}//${location.host}/ws/rooms/demo?token=${encodeURIComponent(guest.token)}`);
socket.onmessage = e => console.log(JSON.parse(e.data));
// After CONNECTED appears, send from one tab:
socket.send(JSON.stringify({type: 'MESSAGE', payload: {text: 'hello'}}));
// To disconnect:
// socket.close();
```

## Wire contract and message flow

`POST /auth/guest` returns HTTP 201 with `{ "user_id": "user-...", "token": "..." }`.
The opaque token is a credential generated by the server; a user ID is not a token.
Keep it private. Tokens last for the process lifetime in this milestone; expiry
and revocation are not implemented. Query tokens support browser WebSockets;
configure deployments to avoid logging query credentials and use HTTPS/WSS.

Connect to `/ws/rooms/{room_id}?token=...`. Room IDs contain 1–64 ASCII letters,
digits, underscores, or hyphens. Invalid credentials or room IDs are rejected
before accepting the socket (typically HTTP 403 during the handshake).

The socket first receives:

```json
{"type":"CONNECTED","user_id":"user-123","room_id":"demo"}
```

Client sends a JSON text frame:

```json
{"type":"MESSAGE","payload":{"text":"hello"}}
```

Transport parses the envelope and calls `GameRuntime.handle` with the room from
the URL and user from authentication. The runtime constructs this server event,
then calls the `Broadcaster` to deliver it to other users in that room:

```json
{"type":"MESSAGE","sender_id":"user-123","payload":{"text":"hello"}}
```

Client envelope fields such as `sender_id` and `room_id` are ignored. Payloads are
untrusted application data, not identity or routing instructions. `MESSAGE` remains
supported alongside `GAME_COMMAND` (documented below). Malformed JSON, binary frames,
unknown message types, and invalid MESSAGE payloads
receive `{"type":"ERROR","code":"INVALID_MESSAGE",...}` without closing the connection.
No delivery history, replay, acknowledgment, or global event ordering is promised.

## Structure and responsibilities

```text
app/
  main.py                         # App factory, lifespan, dependency wiring
  auth/
    models.py                     # Guest credential response
    service.py                    # AuthService protocol and in-memory guest auth
  transport/
    http.py                       # Health and guest issuance endpoints
    websocket.py                  # Authentication, parsing, runtime dispatch, cleanup
  multiplayer/
    connection_manager.py         # Socket lifecycle, per-socket sends, delivery
    room_service.py               # In-memory membership
    presence.py                   # Online membership snapshots
    broadcaster.py                # Runtime-facing broadcast protocol
  runtime/
    game_runtime.py               # Authenticated message → server event → broadcast
    game_registry.py              # Owns room engines and per-room locks
  games/
    base.py                       # Typed GameEngine protocol and expected rejection
    echo.py                       # PING/PONG test engine
  models/
    messages.py                   # Existing chat envelopes
    game.py                       # GameCommand, GameEvent, CommandError
    room.py                       # Presence snapshot
    user.py                       # Immutable authenticated identity
scripts/client.py                  # Interactive guest client
tests/                            # Unit and WebSocket integration tests
```

Key interfaces:

```python
AuthService.authenticate(token: str) -> UserIdentity                  # async
RoomService.join(room_id: str, user_id: str) -> None                    # async
RoomService.leave(room_id: str, user_id: str) -> None                   # async
RoomService.members(room_id: str) -> list[str]                         # async
ConnectionManager.connect(room_id, user_id, websocket: Socket) -> str  # async
ConnectionManager.disconnect(room_id, connection_id) -> None          # async
ConnectionManager.send_to_user(user_id, message) -> None              # async
Broadcaster.broadcast(room_id, message, exclude_user_id=None) -> None # async
GameRuntime.handle(room_id, user_id, command) -> CommandError | None   # async
GameRegistry.engine_for(room_id: str) -> GameEngine | None
GameEngine.handle_command(user_id: str, command: GameCommand) -> list[GameEvent]
```

`connect` registers an already accepted socket and returns a unique connection ID.
`disconnect` uses that ID, so an old connection cannot remove another tab or a
reconnected client. Membership persists until the user's last socket in the room
closes. Sender exclusion applies to all sockets belonging to that identity;
`send_to_user` addresses that user's sockets across all rooms. Membership describes
online users only, not persistent seats in a future game.

The connection manager coordinates lifecycle changes under an async lock and calls
the room service for membership changes. Application code should use the manager
for socket lifecycle, not independently alter membership. Broadcast snapshots
connections under the lock, releases it before network I/O, and sends concurrently
to recipients. Per-socket locks serialize writes. Failed or timed-out sends remove
only the affected connection and attempt to close it. Default send timeout is five
seconds. These guarantees target normal asynchronous use within a single event
loop, not multiple processes or threads. Delivery is best effort; a slow recipient
can delay completion of the sender's handler up to the send timeout.

Presence is exposed internally through `PresenceService.snapshot` and in the
authenticated `GET /rooms` directory. The test console polls the directory every
two seconds; presence notifications are not broadcast.

Authentication can be replaced by assigning a new `AuthService` implementation at
the composition root. Guest issuance is separate from the transport's authentication
interface. Future storage should sit behind the owning auth/room services; there
is no generic repository layer or distributed coordination yet.

## Game command runtime (Milestone 2)

The existing auth, membership, presence, connection manager and broadcaster are
reused. `GameEngine` remains independent of FastAPI, sockets, authentication and
broadcasting. It validates semantics before state mutation and returns typed events.
`GameRuntime` knows no command names. Adding future game commands changes the
selected engine, not the transport or runtime.

```text
Client: GAME_COMMAND
  → WebSocket: parse envelope; use authenticated user and URL room
  → GameRuntime: look up room engine and acquire its lock
  → GameRegistry: room → engine + lock
  → EchoGameEngine: validate PING, increment room-local counter, return PONG
  → GameRuntime: serialize returned GameEvents in order
  → ConnectionManager (Broadcaster): send to every connection in that room
  → Clients: GAME_EVENT, including the requesting player
```

Example command:

```json
{"type":"GAME_COMMAND","command":"PING","payload":{"message":"hello"}}
```

Example server result (identity comes from authentication):

```json
{"type":"GAME_EVENT","event":"PONG","payload":{"message":"hello","player_id":"user-123","sequence":1}}
```

The `payload` defaults to a fresh object. Command/event names must be nonblank
strings. Client-supplied envelope `user_id`, `sender_id`, and `room_id` are ignored;
payload fields are untrusted game data and never replace routing or identity.
PING accepts an optional string `message`; it does not echo arbitrary identity fields.

The composition root (`app/main.py`) selects EchoGameEngine for this milestone.
Its `provision_room` hook registers one instance on HTTP room creation or an
authenticated WebSocket join to an ad hoc room. Registry lookup does not implicitly
create engines. Repeated joins reuse the same instance. Different rooms cannot
register the same instance, and existing entries cannot be overwritten.
The registry owns engines and their locks until application shutdown, including
when a room becomes empty. This deliberately preserves state over reconnects.
Ad hoc rooms may disappear from the presence directory while their engine remains.
There is no room deletion, engine replacement, eviction, persistence or reset API
in this milestone. Restart clears engines along with the other in-memory services.

Concurrency invariant: within one process/event loop, the room lock covers the
entire synchronous engine call and all broadcasts for its event batch. Same-room
commands cannot mutate state or deliver event batches out of order. Different
rooms use different locks, so network waits in one room do not block another.
Engines must be short synchronous operations without blocking I/O; CPU work still
shares the event loop. Chat retains its existing ordering semantics and is not
serialized with game commands. Broadcast delivery remains best effort; there is
no rollback, replay or exactly-once delivery on disconnect/cancellation. Unexpected
engine failures are reported but cannot automatically undo engine mutations.

Errors are returned only to the requesting connection (not all tabs for that user):

```json
{"type":"ERROR","category":"game","code":"UNKNOWN_COMMAND","detail":"This test engine supports PING."}
```

| Category | Codes | Meaning |
| --- | --- | --- |
| transport | INVALID_MESSAGE, INVALID_COMMAND | Invalid JSON/frame/type or malformed envelope |
| infrastructure | ENGINE_NOT_FOUND, ENGINE_FAILURE | Missing engine or unexpected engine exception |
| game | UNKNOWN_COMMAND, INVALID_PAYLOAD | Test engine rejected the command |

An invalid command does not close the socket. Expected rejections use
`GameCommandRejected`; engines must reject before mutation. Unexpected exceptions
are logged server-side and returned with a generic detail. Engines return errors
to the runtime; the transport sends them through the existing connection manager.

### Standalone Call Break trick validator

The trick validator is implemented in `callbreak/rules.py`, using
immutable models in `callbreak/models.py` and shared cards in `card_utils/cards.py`.
It supports four or five players, with local IDs 1 through the player count.
It has no imports from the multiplayer application or third-party libraries.

```python
from card_utils import Card
from callbreak import Play, Trick, legal_cards, validate_play

trick = Trick(player_count=4, leader=1, plays=(Play(1, Card.parse("10H")),))
hand = tuple(Card.parse(value) for value in ("5H", "QH", "AS"))

assert legal_cards(hand, trick, player_id=2) == (Card.parse("QH"),)
error = validate_play(hand, trick, player_id=2, card=Card.parse("5H"))
assert error.code == "ILLEGAL_CARD"
assert validate_play(hand, trick, player_id=2, card=Card.parse("QH")) is None
```

Supply the server's authoritative remaining hand, never a client-reported hand.
Validation returns `None` for an allowed move or a `PlayRejection` with code/detail;
malformed domain snapshots raise `ValueError`. It does not mutate state.
`current_winner(trick)` returns the leading Play, and `resolve_trick(trick)` returns
the winning player ID only when everyone has played. Match-phase checks, history
audits and redeals are implemented in the surrounding standalone modules;
the test console uses the separate `/test-games` host rather than the generic game runtime.
Run these tests with `python -m pytest -q tests/test_callbreak_rules.py`.

FastAPI reference: [WebSockets](https://fastapi.tiangolo.com/advanced/websockets/).


## Browser test console

Start the server using the instructions above, then open **http://127.0.0.1:8000/**.
No separate frontend server, build step, or external asset service is needed.

1. In the first tab, select **Sign up** and enter a username (3–32 letters, numbers,
   underscores or hyphens) and a test password (8–128 characters). Sign-up signs you in.
2. Enter a room name and click **Create**. The console creates and connects to it.
3. Open a fresh second tab at the same URL. Create a different account or use
   **Continue as guest**, then select the room from the directory or paste its ID.
4. Wait for **Connected** in both tabs. Send a message and confirm it appears in
   the other tab. Your own message is labeled as locally sent, not acknowledged.
5. Click **Leave** and check the connected member count in the other tab. Sign out
   and use **Sign in** to return to an existing account while the server is running.
6. Expand **Event inspector** to see the last 100 sent/received WebSocket events.
   This also displays future event types even if the chat view does not handle them.

Sessions use per-tab `sessionStorage` and survive page refresh. Some browsers copy
sessionStorage when duplicating a tab: sign out in the duplicate and choose a
separate identity to test broadcasts. Signing out closes this tab's socket and
clears its local session; it does not revoke other sessions or the server token.
Selecting a room switches connections. A dropped connection offers manual rejoining.
Chat history is local, capped at 200 messages, and cleared on room changes/sign-out.

The console is disposable test tooling in `app/test_ui/`; FastAPI serves its static
HTML/CSS/JavaScript. Accounts and room creation are backend services, so a future
client can use the same HTTP and WebSocket endpoints. The console now supports the test engine command/event path alongside chat.

Additional API endpoints:

| Endpoint | Purpose |
| --- | --- |
| `POST /auth/signup` | Create a test account with `{username, password}`; returns `{username, user_id, token}` |
| `POST /auth/signin` | Issue a new session for an existing account |
| `GET /auth/me` | Resolve the current bearer token |
| `POST /rooms` | Create an empty named room with `{name}` |
| `GET /rooms` | List created and currently active rooms, including connected member IDs |

The last three endpoints require `Authorization: Bearer <token>`. Both account and
guest tokens work for rooms and WebSockets. Joining remains a WebSocket operation;
creating a room does not itself add membership. Usernames are case-insensitive.
Passwords are stored only as randomly salted scrypt hashes, computed off the event
loop. Account authentication remains behind the existing `AuthService` interface.
This is local test authentication: accounts, hashes, and tokens are in memory;
expiry, rate limits, password recovery, and durable storage are not implemented.

Implementation references: [Python password key derivation](https://docs.python.org/3/library/hashlib.html#key-derivation)
and [FastAPI static files](https://fastapi.tiangolo.com/tutorial/static-files/).
